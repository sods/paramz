# CIP-0003: Notifying parameter reload API

## Status

- [x] Proposed
- [ ] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Resolve #51: make the recommended save/load path notify observers. Prefer documentation + `m[:] =` first; consider a careful notifying wrapper only if docs prove insufficient.

## Motivation

`param_array[:] = loaded` updates the shared buffer but does not call `_trigger_params_changed()`, so views and predictions stay stale while the flat array looks correct. Downstream GPy docs repeated this pattern.

## Detailed Description

Two layers (can ship independently):

1. **Docs (cheap):** Clarify that in-place `param_array` writes do not notify; recommend `m[:] = …` or an explicit trigger after deliberate buffer writes. Align README with GPy PR #1221.
2. **Optional API:** Notifying `__setitem__` on the array returned by `param_array`, with deferral while `update_model(False)` so `randomize` / gradcheck batching stays correct.

Do not break the one-copy-in-memory contract: notification is about observers, not about copying buffers.

## Implementation Plan

1. Patch `param_array` docstring and README load example.
2. Add regression test: assign via recommended API → child views / likelihood match.
3. Decide whether auto-notify wrapper is worth the risk; if yes, implement with batching guard.
4. Coordinate close of GPy #1217 once paramz docs/API land.

## Backward Compatibility

Docs-only change is safe. Auto-notify may change timing of `parameters_changed` for code that wrote the buffer and notified manually — preserve `update_model(False)` semantics.

## Testing Strategy

- Unit test in paramz (no GPy required for the core assert).
- Optional GPy integration check for predict-after-reload.
